# Loan Performance Intelligence Engine Constitution

Governing document for the Intain Campus FinTech Challenge 2026 — AI Track submission.

This constitution is derived directly from the challenge's own scoring rubric (§12 Judging
Criteria) and its failure list (§13 Low-Score or Disqualification Conditions). Every principle
below exists to make a disqualification condition structurally impossible rather than merely
discouraged.

## Core Principles

### I. ML-First — The LLM Never Decides (NON-NEGOTIABLE)

Every predicted quantity delivered to a consumer — probabilities, next state, anomaly score,
exception type, confidence — MUST be produced by a non-LLM statistical or machine-learning
model fitted on training data.

- An LLM MUST NOT be called anywhere on the path that computes a value written to
  `submission.csv`. This is enforced by test, not by convention.
- The LLM's permitted roles are exhaustively: summarizing model output, retrieving and quoting
  data-dictionary definitions, drafting reviewer notes, proposing candidate validation rules for
  human approval, and narrating scenario results.
- Every LLM-authored artifact MUST carry a machine-readable label marking it a
  *recommendation*, never a decision. Reviewer actions remain a human or deterministic-rule
  output.
- Removing the LLM entirely MUST leave the predictive pipeline fully functional. A test asserts
  the pipeline produces a valid submission with the LLM provider disabled.

**Rationale**: §13 disqualifies solutions that "only use an LLM API for prediction" or "do not
train a non-LLM model". §9's qualification rule repeats it. This is the single highest-severity
failure available, so it is made unreachable by construction.

### II. Leakage Containment (NON-NEGOTIABLE)

No information that post-dates a prediction's as-of month may influence that prediction.

- Splits MUST be time-aware: train, validation, and test are separated by `reporting_month`
  cutoffs. Random row-level splitting is forbidden.
- A single `loan_id` MUST NOT appear on both sides of a split boundary unless the split is
  purely temporal and the justification is written into the model card.
- Target columns (`next_3m_delinquency_flag`, `next_6m_delinquency_flag`,
  `next_12m_default_flag`, `next_12m_prepayment_flag`, `next_state`, `exception_required`,
  `exception_type`) MUST NOT appear in any feature matrix, nor may any feature be derived from
  them. An automated check fails the build if a target name or target-derived column reaches a
  fitted estimator.
- Lagged and rolling features MUST be computed strictly from rows at or before the as-of month,
  grouped by `loan_id`, with no centred or forward-looking windows.
- Preprocessing statistics (imputation values, scalers, encoders, target statistics) MUST be fit
  on training data only and applied to later periods — never fit on the full panel.
- A leakage audit artifact MUST be emitted on every run, listing split boundaries, per-split row
  and loan counts, boundary overlap counts, and the feature-name screening result.

**Rationale**: §13 disqualifies both "random splits that leak the same loan across train and
validation" and "leaks target labels into features". Leakage also silently inflates every metric
in §12, making an otherwise honest submission indefensible under questioning.

### III. Grounded LLM Governance

LLM usage MUST be observable, attributable, and challengeable after the fact.

- Every call MUST append a record to an append-only prompt log containing: UTC timestamp,
  provider, model identifier, full rendered prompt, full raw response, token counts, latency,
  the grounding context supplied, and the resulting accept/reject decision.
- Generated text MUST be grounded: every factual claim about a loan, a metric, or a field
  definition MUST be traceable to supplied context (model output, retrieved data-dictionary
  entry, or validation rule). A citation/consistency validator runs on each generation; failures
  are rejected and logged, not silently shown.
- Numeric claims in generated text MUST be checked against the source values that were supplied
  to the model. A mismatch is a rejection.
- A curated rejection log MUST be maintained with concrete examples where the LLM was wrong,
  vague, or overconfident, each annotated with what failed and how it was caught.
- The system MUST remain fully operable with no LLM provider configured, degrading to
  deterministic templated notes rather than erroring.

**Rationale**: §12 awards 10 points for "Smart LLM Usage" specifically scoring grounding,
prompt logs, and hallucination controls. §13 penalizes "LLM-generated narratives without
grounding". §7 Task 7 explicitly requires logging and wrong-output examples.

### IV. Reproducibility by Construction

A judge MUST be able to reproduce every delivered number from a clean checkout.

- One documented command MUST take raw input data to `submission.csv` plus all reports. No
  undocumented manual step may sit between raw data and any deliverable.
- All randomness MUST derive from a single configured seed threaded explicitly into every
  splitter, sampler, model, and simulator. Nothing may rely on an unseeded global default.
- Dependencies MUST be pinned to exact versions in a committed lockfile-style requirements file,
  installed into a project-local virtual environment.
- Schema, paths, split boundaries, hyperparameters, and scenario assumptions MUST live in
  version-controlled configuration, not in literals scattered through code. Swapping the input
  dataset MUST be a configuration change, not a code change.
- Row ordering in all written artifacts MUST be deterministic via explicit sort keys.
- Data files MUST NOT be committed to the repository; their provenance, licence, and retrieval
  steps MUST be documented instead.

**Rationale**: §13 disqualifies "provides no reproducible code". §12 awards 5 points for ML
Engineering and Reproducibility. Determinism is also the precondition for Principle V — an
unreproducible number cannot be honestly defended.

### V. Honest Reporting & Declared Limits

Reported results MUST correspond to computations that actually executed.

- Every metric appearing in any report, slide, or README MUST be read from a metrics artifact
  written by the run that produced it. Hand-typed numbers are forbidden.
- Placeholder, illustrative, or expected values MUST NOT appear in any deliverable. If a
  component did not run, the deliverable MUST say so explicitly.
- Metrics MUST be reported with the split they came from and the class balance behind them. A
  bare accuracy or AUC without denominator context is incomplete.
- Every model MUST ship a model card stating objective, data, features, model type, validation
  method, metrics, leakage controls, limitations, and known failure modes.
- Error analysis MUST include concrete false positives and false negatives, and calibration MUST
  be reported alongside discrimination.
- Where a required capability is approximated rather than fully implemented, the approximation
  MUST be named as such in the model card.

**Rationale**: §13 disqualifies "fabricates results", "provides no evaluation metrics", and
"cannot explain model behavior". §12 awards 10 points for Explainability and Responsible AI,
which explicitly includes limitations.

### VI. Deliverables Are Build Outputs

Every §11 deliverable that is a computed artifact MUST be generated by the pipeline, not assembled by
hand at the end. §11 lists ten deliverables; six are computed artifacts and are therefore bound by
this principle (`submission.csv`, model card, data intelligence report, explainability report,
scenario report, LLM copilot output). The remaining four are authored rather than computed — the
repository itself, the source code, the AI Development Log, and the demo video — and are governed by
the incremental-authorship rule below rather than by code generation.

- The data intelligence report, explainability report, scenario report, model card, metrics
  tables, and `submission.csv` MUST each be written by code as a pipeline stage.
- `submission.csv` MUST be validated against the required column contract before the run is
  considered successful — column names, order, dtypes, value domains, row count, and absence of
  nulls in required fields.
- The AI Development Log MUST be maintained continuously during development, capturing tools
  used, representative prompts, accepted and rejected outputs, the human review process, and
  approximate AI-generated code share. It MUST NOT be reconstructed from memory afterwards.
- The demo surface MUST read the same artifacts the reports read, so the app and the documents
  can never disagree.

**Rationale**: Hand-assembled deliverables drift from the code that produced them, which
converts a Principle V violation into an accident. §14's fifteen-step demo flow also requires
every stage to have a real inspectable output.

## Technology & Data Constraints

**Language & environment**: Python 3.11 in a project-local `.venv`. No global installs.

**Modeling stack**: scikit-learn (preprocessing, calibration, metrics, baselines,
IsolationForest), LightGBM and XGBoost (gradient-boosted primary models), lifelines
(survival/hazard), SHAP (attribution), statsmodels and scipy (statistical tests, drift),
pandas/numpy/pyarrow (data).

**Interfaces**: A headless CLI is the source of truth for all computation. A Streamlit
multi-page app is the demo surface and MUST be a read-only consumer of artifacts the CLI wrote.
The app MUST NOT be the only way to produce any deliverable.

**LLM provider**: Groq, running a Qwen instruct model, accessed through a provider abstraction.
The model identifier MUST be configuration, not a literal, because hosted model availability
changes. Credentials come from the environment only; keys MUST NOT be committed. A deterministic
offline provider MUST satisfy the same interface so the repository runs without credentials.

**Data terms compliance**: §13 lists "uses public data in violation of source terms" as a
disqualification condition. Datasets MUST be obtained from the issuing institution under its own
accepted terms, never from third-party redistributions. Source, retrieval date, and licence terms
MUST be recorded in the data provenance documentation. Raw and derived data files stay
git-ignored.

**Feature-engineering constraint**: All panel features MUST be constructed through a shared
as-of-month-aware transformation layer that enforces Principle II mechanically. Ad-hoc feature
computation inside notebooks or model scripts is forbidden.

## Development Workflow & Quality Gates

**Test obligation**: Tests are MANDATORY for this project, not optional. The feature
specification MUST explicitly state this so the tasks template's conditional test clause is
satisfied. At minimum the suite MUST include:

1. A leakage guard asserting no target-named or target-derived column reaches a fitted estimator.
2. A temporal-split test asserting train/validation/test month ranges are disjoint and ordered.
3. A determinism test asserting two seeded runs produce byte-identical submission output.
4. A submission-contract test validating schema, dtypes, value domains, and null policy.
5. An LLM-absence test asserting the full pipeline succeeds with the provider disabled.
6. A grounding-validator test asserting fabricated numeric claims are rejected.

**Definition of done** for any unit of work: it runs from the CLI, it writes an inspectable
artifact, it is covered by at least one test, and any number it reports is read from that
artifact.

**Gate ordering**: Data contract and profiling MUST precede feature engineering. Feature
engineering MUST precede modeling. The leakage audit MUST pass before any metric is reported.
Submission validation MUST pass before a run is called successful.

**Constitution Check Gates** — `/speckit-plan` MUST populate its Constitution Check section with
these, and each MUST be answerable with a specific file or test:

| Gate | Question the plan MUST answer |
|------|-------------------------------|
| G1 (Principle I) | Which non-LLM model owns each submission column, and which test proves no LLM is on that path? |
| G2 (Principle II) | Where are split boundaries defined, and which test enforces target exclusion and temporal disjointness? |
| G3 (Principle III) | Where is the prompt log written, and what validator rejects ungrounded output? |
| G4 (Principle IV) | What is the single command, where is the seed threaded, and where are versions pinned? |
| G5 (Principle V) | Which artifact does each reported metric come from, and where is the model card generated? |
| G6 (Principle VI) | Which pipeline stage writes each §11 deliverable, and what validates the submission contract? |

**Complexity discipline**: Prefer the simplest construct that satisfies a principle. Advanced
features from §10 are additive and MUST NOT be pursued before the §9 Minimum Acceptable Solution
is complete and passing its gates. Any deviation from a principle MUST be recorded in the plan's
Complexity Tracking table with the simpler alternative and why it was rejected.

## Governance

This constitution supersedes ad-hoc preference and convenience. Where this document and an
individual implementation choice conflict, this document wins.

**Authority**: Principles I and II are non-negotiable and MAY NOT be suspended for any reason,
including deadline pressure, because each maps to an explicit disqualification condition.
Principles III through VI MAY be narrowed only by a recorded amendment.

**Amendment procedure**: Amendments MUST be made in this file, MUST state the motivating problem,
MUST update the version line, and MUST update the Sync Impact Report at the top of this file with
affected templates and artifacts. Downstream artifacts (`spec.md`, `plan.md`, `tasks.md`, model
card, README) MUST be re-checked for consistency in the same change.

**Versioning policy**: Semantic versioning. MAJOR for removing or incompatibly redefining a
principle; MINOR for adding a principle or materially expanding guidance; PATCH for
clarifications and wording that do not change obligations.

**Compliance review**: Every substantive change MUST be checked against the six Constitution
Check Gates before it is considered complete. `/speckit-analyze` MUST flag any spec, plan, or
task that contradicts a principle. Any principle violation discovered in review MUST be either
fixed or recorded in Complexity Tracking with justification — never silently accepted.

**Runtime guidance**: `CLAUDE.md` (once generated) and `README.md` provide day-to-day
development guidance and MUST NOT contradict this constitution. On conflict, this file governs
and the guidance file MUST be corrected.
